# 2.8 审核分工与缺口补审

每位审核员可配置自己的分工、范围、提示词和必查清单，继续独立选择引擎、模型及思考强度。必查清单每行一项，最多 20 项，每项最多 2000 字符，不接受重复项；可随团队模板保存和应用。

## 使用流程

1. 在并行审核中配置审核员及其必查清单，启动审核。
2. 报告逐项展示已检查、未检查或有争议，以及对应证据。已检查表示执行了检查，不表示不存在 Bug。
3. 在“审核分工与缺口补审”中选择仍未完成的项目，单次最多 20 项，启动补审。
4. 补审继承对应审核员的模型、思考强度和提示词，使用新会话生成独立审核记录。通过关联按钮查看原审核及补审。

原报告、发现和覆盖证据保留。补审只对所选缺口负责，即使补审完成，原审核仍保留原状态，不会自动合并覆盖范围或宣称整个工程已审完。更换团队配置时请另建审核。

## 完整性与并发约束

- Agent 没有返回某条必查项的结果时，该项归为未检查，审核不能标记完整。
- 缺口来源包括未完成的必查项、结构化覆盖范围中的未检查或争议项，以及失败或不完整审核员的范围兜底。
- 补审前校验报告版本、项目路径及源码指纹；源码改变或报告过期后须重新审核或刷新报告。
- 有其他工作流正在运行，或旧审核进程仍存在时，阻止补审启动。
- 长范围说明保留在补审提示词和来源记录中，必查项使用带来源编号的短名称引用。
- 旧报告没有必查清单时保持原有行为；本版不增加争议自动裁决，也不自动关闭发现的问题。

## 协议

审核员配置新增 `checklist: string[]`。报告新增 `taskChecks: [{id, status, evidence}]`；ID 为对应清单顺序的 `C-1`、`C-2` 等，状态为 `CHECKED`、`UNCHECKED` 或 `DISPUTED`。未知 ID、重复 ID、空证据及相互矛盾的完成声明会被拒绝。

`GET /api/audits/:id` 增加 `gaps` 和 `supplementVersion`。`POST /api/audits/:id/supplement` 接收 `workspaceRoot`、`version`、`selections: [{reviewerId, taskId}]`，服务器从原记录解析所选缺口，成功返回 202 和新 `auditId`。子记录的 `parentAudit` 和原记录的 `supplementRuns` 保留关联。

验收情况见 [2.8 验收记录](version-2.8-acceptance.md)。
