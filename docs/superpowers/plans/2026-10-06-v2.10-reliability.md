# 2.10 稳定性与恢复 Implementation Plan

> **For agentic workers:** 按任务复选框实施。若有 superpowers:executing-plans 可使用；没有技能也可按本文逐项执行。用户额度有限，默认单 Agent，不自动委派。

**Goal:** 使旧记录、损坏数据、服务重启及验收环境具备可诊断、可恢复的确定行为。

**Architecture:** 保留 RunStore 和现有工作流，新增存储归一化及运行租约模块；工作流继续负责业务状态，公共层负责文件与进程所有权。迁移和测试均不覆盖用户原始数据。

**Tech Stack:** Node 内置 fs/path/crypto/child_process、PowerShell 7、原生前端；Playwright 仅作为可选验收工具。

**Spec:** [总体设计](../specs/2026-10-06-next-versions.md)，配合 [验证手册](../../handoff/ENGINEERING_GUIDE.md)。状态：待实施。

## Global Constraints

Windows / PowerShell 7 / Node.js 18+；后端零新增 npm 运行时依赖；默认一个全局工作流；原报告与旧记录保留；失败不算通过；真实模型调用、Git 提交与推送不在默认范围。

const fs=require('fs'),os=require('os'),path=require('path');
const {RunStore}=require('../../engine/run-store');

## Task 2：存储版本、诊断和显式迁移

**Files:** 新建 `engine/storage-schema.js`、`engine/storage-migration.js`、`tests/storage-migration.tests.js`；修改 `engine/run-store.js`、`server.js`；新增简洁维护区到 `public/index.html`/`public/app.js`。

**Interfaces（新接口草案）:**

```js
normalizeRecord(kind, raw); // 返回新对象；不修改 raw；缺失 storageVersion 当作 0
validateRecord(kind, raw); // {ok, errors:[{path,code}]}
planMigration(store); // {version, entries:[{kind,id,beforeHash,from:0,to:1}], errors:[]}
applyMigration(store, {version}); // 先校验整批版本，再备份和逐项原子替换
```

`storageVersion: 1` 独立于已有业务 `schemaVersion`。保留未知字段、原创建时间、审批/证据历史。未来 storageVersion 大于支持值时禁止写入，不将它当成旧版本降级。

- [ ] 先写失败测试：缺失版本→内存归一化；未来版本→拒绝写；坏 JSON→诊断包含 kind/id，不被当成“没有任务”。

```js
const future={id:crypto.randomUUID(),storageVersion:99};
assert.throws(()=>normalizeRecord('audits',future),/UNSUPPORTED_STORAGE_VERSION/);
assert.equal(JSON.stringify(raw),before); // normalize 后仍不改输入
```

- [ ] 增加 `RunStore.listWithDiagnostics(kind, workspace)` 返回 `{records, errors}`；原 `list()` 保持数组接口以免破坏旧调用。维护页展示诊断，不能静默删除坏文件。
- [ ] 实现迁移预览版本摘要：包括文件 ID 和内容哈希；执行前若任一输入变化返回 `MIGRATION_VERSION_CONFLICT`，不得部分采用旧预览。
- [ ] 备份到数据根 `backups/<operationId>/...`，先持久化迁移 journal，再逐文件 atomicJson；模拟第2条写失败，恢复后可重试且不覆盖首次备份。
- [ ] `GET /api/maintenance/storage` 只预览；`POST /api/maintenance/migrate {version}` 显式执行，活动任务或残留进程存在时409。GET 不自动迁移。
- [ ] 前端显示待迁移/损坏/未来版本数量，显示实际备份位置及每项结果；不要一次加载全部原始源码日志。
- [ ] 验证迁移后原始回答/测试附件引用仍存在；历史人工验收不得被“修正”为当前有效，若版本摘要改变则要求重新验收。
- [ ] 执行 storage 两个测试文件和 audit/planning 兼容测试。

交付：可预览、备份、重试的迁移；损坏记录可定位且不妨碍其他健康记录的查看。

## Task 3：统一运行租约与残留进程保护

**Files:** 新建 `engine/runtime-guard.js`、`engine/process-owner.js`、`tests/runtime-guard.tests.js`；修改 `server.js`、`engine/process-runner.js` 及 workflow/audit/planning 的启动与释放边界。

**Interfaces:**

```js
// owner: {kind,id,workspaceKey}; kind 为 run/audit/planning/health/maintenance
await guard.acquire(owner); // -> {token, release()}; 任一 await 前先占位
await inspectProcess(pid); // {state:'ALIVE'|'EXITED'|'UNKNOWN',startedAt:null|string}
await guard.recover(); // {state:'IDLE'|'BUSY'|'NEEDS_ATTENTION',owner,reason}
```

- [ ] 写竞争测试：两个 acquire 同时执行，只一个成功；第二个不能在第一个 snapshot/preflight 等待期间插入。
- [ ] 在数据根增加独占实例锁，记录 PID 和可核实的启动时间。PID 被复用时不误认旧实例；无法核实所有权时保守报告 UNKNOWN，不自动杀进程或删锁。
- [ ] 每个顶层命令只 acquire 一次。启动返回202后租约持续到 active.promise 结束；stop 先终止子进程并等待，再释放。内部子调用不重复获取同一全局租约。
- [ ] 接入所有入口：普通运行、修复、并行审核、补审、验证、验收测试、讨论、真实模型探测、维护迁移。纯列表/状态/证据读取不持有长写锁。
- [ ] 把兼容接口也走同一防重叠入口，保留当前 UI/SSE 状态契约；不能只改新端点。
- [ ] 测试停止发生在 snapshot、preflight、已spawn、退出回调、响应解析各阶段；释放幂等，异常不泄漏租约。
- [ ] 恢复仅识别/展示孤儿进程，不自动重放 Agent 或付款请求。维护页提供诊断说明；终止不明进程必须另行确认归属。
- [ ] 运行 `node --test tests/runtime-guard.tests.js tests/audit-api.tests.js tests/planning-api.tests.js tests/workflow-api.tests.js`。

交付：跨入口共享同一生命周期；单服务实例限制可解释；不能用“没有 active 对象”当作旧进程已退出。
