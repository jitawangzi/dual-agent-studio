# 2.6：草稿恢复、局部重试与版本对比

## 人工决策草稿

取舍、判断依据、验收条件和业务答复在输入后立即备份到当前浏览器，停止输入约 600 毫秒后保存到服务端。允许未填完的草稿；批准时仍要求完整合法的决策。也可点“立即保存草稿”，确认“已同步”后关闭页面。

重新打开讨论记录会恢复服务端草稿，当前浏览器有尚未同步的同版输入时优先保留该输入。浏览器备份不可用或服务端保存失败会显示提示。团队配置仍沿用原来的浏览器保存方式。

同一讨论采用独立草稿版本号，旧页面不能静默覆盖新页面。冲突时保留本页输入，并显示服务端草稿供比较。可以“使用服务端草稿替换本页”，或者“用本页草稿覆盖所示版本”。覆盖仍检查版本：期间其他页面再修改，会再次冲突。审批也检查草稿版本，旧预览不能绕过他人的更新。

服务端草稿位于 `.studio/discussions/<id>/draft.json`，不修改目标工程。它与正式讨论版本分开，保存草稿不触发 Agent 调用，不代表批准，也不改变已批准方案。草稿绑定讨论版本，不能把旧轮次的提案 ID 直接应用到重试后的新版本。

## 失败定位与局部重试

调用记录区分回答已验证、回答格式/内容不合规、调用超时、调用失败、停止及中断。无效回答会保留原文，不能显示为有效步骤完成。进度统计已通过的步骤数，同时显示总尝试次数。

失败、停止或中断的讨论可以点击“重试失败 / 未完成步骤”：

- 检查讨论版本和旧进程，使用原团队配置和新的调用会话。
- 已有源码指纹必须与当前工程一致；不一致时标记失效，不调用 Agent。应创建新版讨论重新调查。
- 有效调查和提案保留；仅缺失或失败步骤再次执行。
- 如果需要重做调查，下游提案与质询全部失效；如果需要补做提案，旧质询全部失效。全部提案完整后才启动交叉质询。
- 如果仅质询失败，已通过的其他成员质询保留。
- 不自动无限重试。已完成或已批准的讨论不支持局部重跑，需要补充意见创建新版。

旧版记录里“调用完成”不必然代表输出结构有效；重试依据已保存的调查、提案和质询成果，不以旧调用状态单独认定成功。

## 上一版方案对比

通过补充意见创建新版讨论后，页面增加“与上一版方案对比”。显示新增、移除和修改的提案，以及做法、收益、风险、不包含的范围、人工取舍、验收条件、业务答复及总体范围变化。

生成批准前预览时，对比会加入本次人工输入。批准后恢复展示对应正式决策。未生成预览前，对比是当前模型提案与上版方案的比较，不代表输入已获批准。

提案 ID 只在单次讨论内有效，因此只用唯一的“角色名称 + 标题”做对应；名称改变或匹配不唯一时保守显示为新增/移除。没有使用模型推断同义关系，也不会据此自动采纳方案。当前只比较直接上一版，不提供任意两版选择。

## API

- `GET /api/planning/:id/draft`：读取草稿及 revision。
- `POST /api/planning/:id/draft`：传 `workspaceRoot, version, draftRevision, value`；value 包含 selections 和 answers，可有空字段。
- `POST /api/planning/:id/retry`：传 `workspaceRoot, version`，启动局部重试。
- `GET /api/planning/:id/compare`：读取与上一版的结构化差异；无父记录时为 null。
- preview / approve 增加 `draftRevision`；有已保存草稿时必须匹配。preview 返回 comparison，内容对应即将批准的决策。

无需新增 npm 依赖。2.5 记录可继续读取和批准。使用 Node watch 启动时后端自动加载更新；普通 node 进程需要通过工程启动/重启脚本重新启动。
