# 2.4：跨次问题跟踪与复查

本版围绕审核后的长期跟踪、修复验收和无进展处理，不改变讨论方案需要人工批准的要求。

## 项目问题台账

选择工作区后打开“项目问题台账”。每个问题有稳定的 `ISS-…` ID，展示出现次数、历史人工判断、审核来源、修复记录以及最近复核证据。支持关键词、待处理、复核关闭、再次出现、历史误报、暂缓及证据变化筛选。可以从台账跳回原审核或修复运行。

关联依据是工作区、类别、文件与标准化问题描述（忽略描述大小写及多余空白）。不同项目隔离；不同描述或类别不会被模型自动合并。文件移动、问题改写可能产生新 ID，这一版不提供语义合并。原有历史记录无需迁移，台账按保存的证据生成，不维护另一份可冲突的状态文件。

未在下一次审核中出现不代表修复。只有修复流程中独立复核留下的关闭记录才能显示复核关闭；之后再观察到同一问题会重新打开。失效报告保留作历史参考，不作为新的有效发现。历史误报、暂缓依据可查看；证据或源码指纹变化时提醒重新确认。台账不会把旧分诊自动复制成新审核的修复授权。

台账状态反映已保存记录，不持续扫描实时源码，也不证明工程没有其他 Bug。大量历史记录当前仍在请求时读取聚合，尚未做分页与持久索引。

## 修复后的两步复查

从审核报告确认并选择问题进入修复后，流程变为：开发修复 → 测试门禁 → 逐项定向复查 → 整体回归审核。

定向复查使用已配置的审查方模型、思考强度和独立于开发方的审查会话；不是额外要求安装一个 Provider。它收到旧问题的触发条件与验收要求、审核验证记录、开发报告、实际测试结果，以及 Git diff HEAD（最多 32,000 字符）。未跟踪文件不在该 diff 内；提示词要求读取真实源码。非 Git 项目仍可核查源码。

每项待解决问题必须恰好返回一条 RESOLVED、UNRESOLVED 或 DISPUTED 及具体证据。缺项、重复 ID、未知 ID、格式错误都不能关闭问题。RESOLVED 还要求同一源码指纹的测试通过；定向复查后仍要整体审核，并达到连续通过轮数。两阶段结论矛盾不能关闭旧问题；争议会暂停，请人处理。定向复查发现源码被改动则失败。

“轮次流转”新增“定向复查与进展”，保留各轮逐项结论。既有直接需求/方案模式保留原整体审查流程；额外的定向阶段在审核导入的修复运行中启用。

## 无进展暂停与继续

左侧“连续无进展轮数上限”默认 3，可设 1–10。第一份完整审核结果建立基线；此后每轮没有关闭基线中待解决的问题、也没有通过完整验收时，计数加一。新增更多问题、改写总结或只改变源码指纹不算有效进展。关闭已有问题或通过完整审核会清零。

达到上限时状态为 NEEDS_ATTENTION，保存待解决 ID 和各轮进展依据。测试连续失败耗尽原“自愈重试上限”时，也改为人工决策状态。CLI 崩溃、无效输出等执行错误仍为失败，不伪装成人工验收。

在轮次页填写决策依据和追加轮数后继续。不会直接关闭问题；会清除本次停滞基线，重新测试、复核当前源码，再决定是否需要开发修改。方案模式改变范围仍需先批准新版方案。

## API 与兼容

- `GET /api/issues?workspace=…`：必须指定工作区，返回从历史审核与运行聚合的台账。
- `POST /api/runs`、`POST /api/audits/:id/repair`：新增 `maxNoProgressRounds`，默认 3。
- 运行记录新增可选的 `targetedReview`、`targetedReviewHistory`、`progressCheckpoint`、`progressHistory`、`attention`，旧记录仍可读取。
- 沿用 `/api/runs/:id/decision` 处理人工决策和 `/api/stop` 停止，不自动重放中断的开发修改。

启动脚本当前为 `restart.ps1` / `restart.bat`，使用 `node --watch`。自动重载会中断正在运行的任务，应在空闲时更新服务代码。
