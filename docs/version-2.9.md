# 2.9 审核闭环总览与人工验收

审核报告中新增“审核闭环总览与人工验收”，汇总一组原审核、补审、关联重新审核及修复运行。原始报告保持原状态；总览根据持久化证据计算当前进度，人工验收独立留痕。

## 使用方式

1. 打开审核报告，查看范围与必查项是否完成，以及每项证据的来源。
2. 从问题待办跳转到来源报告，完成分诊、选择修复或查看修复运行。待确认、待修复和待独立复核都会阻止验收。暂缓或排除必须在原分诊中填写理由，理由会保留在总览中。
3. 有缺口时，从对应报告选择补审。一次补审新发现的范围缺口不会被另一次成功补审掩盖。
4. 点击“刷新闭环与源码状态”核对当前文件。源码变化后，旧覆盖证据不能继续当作当前检查；点击“按原团队重新审核当前源码”，启动使用原团队模型、思考强度、提示词和必查清单的新审核。
5. 填写测试命令并勾选确认执行。命令在目标工程中真实运行，提供退出状态及日志。也可以使用关联修复运行的测试证据；以最近执行记录为准，要求源码指纹一致、执行成功且测试没有修改源码。
6. 必查范围完成、待处理问题解决、测试通过后，填写人工验收说明并确认。暂缓项仍然显示，不会冒充已修复。验收记录保存当时的源码、证据版本、说明和暂缓项。

## 完整性规则

- 已检查只表示该范围执行过检查，不保证工程没有 Bug。
- 必须同时满足关联修复运行通过、测试版本匹配、逐个 Bug 的独立关闭证据匹配当前源码，才能显示“已独立复核关闭”。仅有整轮通过结论不够。
- 修复循环中的后续改动会将旧版本已关闭的 Bug 转回待验证，先重新逐项复核，再做整体回归。
- 同一问题在更新的审核中再次出现时，按实际发现时间保留新证据；旧修复不能关闭新发现。未再提及某问题不等于已修复。
- 新的完整重新审核建立新的覆盖基准；原发现仍保留，不能通过重新审核绕过问题处理。
- 页面验收说明绑定填写时的证据。证据更新后需要重新核对和编辑说明；服务端会再次核验源码、版本和全部门槛。重复提交相同有效验收不会新增重复记录。
- 历史验收不会被删除，后续源码或证据变化会使其不再显示为当前有效。
- 测试可停止；服务重启会记录中断。若旧测试进程仍存活，会阻止新的写入操作，避免与新工作流重叠。

## 接口与边界

- `GET /api/audits/:id/closure`：当前源码上的覆盖、问题、测试、验收门槛、版本及历史。查看子审核也会汇总到原审核组。
- `POST /api/audits/:id/closure-test`：传入 `workspaceRoot`、`command` 和 `execute: true`，异步执行真实测试。
- `POST /api/audits/:id/closure-recheck`：传入 `workspaceRoot`，按原团队启动新的完整关联审核，使用新会话。
- `POST /api/audits/:id/closure-accept`：传入 `workspaceRoot`、最新 `version` 和非空 `note`，保存人工验收。

本版只汇总明确关联的审核组，不自动合并项目内所有独立审核。源码变化采用整个源码指纹保守判断，没有按文件依赖推断局部证据仍有效。测试是否充分仍需人工判断；工具不替你选择测试命令，也不会自动批准验收。

验收情况见 [2.9 验收记录](version-2.9-acceptance.md)。
